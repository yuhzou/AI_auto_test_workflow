> 让每一行需求，都能被追溯到一条可独立运行的自动化用例。
>

## 一、核心流程设计
```plain
需求文档  →  结构化需求  →  逐条用例  →  真实系统探索  →  pytest脚本  →  独立回放
  (输入)      (REQ编号)     (评审凭据)    (证据留存)      (可执行)      (可复现)
```

每一个箭头都有**强制门禁**，每一个产物都有**唯一事实源**。模型负责理解、设计与判断，脚本负责格式转换、准入校验与结果记录。**人不写定位器，不抄页面，不靠口述结论。**

## 二、给管理者的五个价值主张
### 1. 需求即追溯，覆盖可证明
每一条需求都有 `REQ` 编号，每一条用例都关联到具体 `REQ`。覆盖率脚本不只统计数字，而是**逐条核对关联与编号**。需求变更时，受影响的用例一目了然——不再是"我觉得覆盖了"，而是"我可以证明覆盖了"。

### 2. 用例质量有评分，不靠平均分蒙混
每条用例都要经过**逐条评审**：预期来源、步骤可执行性、数据与前置条件、场景覆盖。评分 ≥ 75 只是模块准入门槛，**任何一条需确认或不合理，都不能被平均分抵消**。评审凭据写入指纹文件，**文件名叫"已评审"不算数，必须重新过门禁**。

### 3. 定位器来自真实系统，不靠人猜
传统自动化最大的维护成本是"定位器猜不准"。我们的做法是：**用例设计阶段不编造任何 URL、DOM、locator**，而是在真实系统中逐条探索，用页面 snapshot 和真实操作代码作为证据，再固化为脚本。需求一变，重跑探索即可，**不必人肉重抄页面结构**。

### 4. 独立回放，换台机器也跑得通
脚本不复用探索会话的残留状态，前置条件由 fixture 或实际操作建立。每条用例独立回放，记录真实退出码、JUnit 和文件指纹。**通过就是通过，产品缺陷复现就是缺陷复现**——不用 xfail/skip 掩盖，不把错误表现改成正确预期。

### 5. 全程留痕，审计可回溯
从需求解析的原始稿，到用例评审的输入指纹，再到探索过程的每一步证据与回放日志，**每一个决策都有凭据可查**。需求、用例、评审、运行状态分别存储，互不串改。出了问题，能回答"这条用例基于哪个需求的哪个版本、在什么环境、用什么数据跑出过什么结果"。

## 三、三大引擎，一条流水线
| 引擎 | 职责 | 管理者关心的问题 |
| --- | --- | --- |
| **req-processor** | 文档 → 结构化需求 + REQ 清单 | "需求有没有被完整理解？模糊点有没有被识别？" |
| **testcase-builder** | 需求 → 逐条用例 + 评审凭据 | "用例靠不靠谱？谁负责逐条把关？" |
| **web-automation** | 已评审用例 → 真实探索 → 脚本 → 回放 | "脚本能跑通吗？换环境还行不行？" |


三个引擎顺序衔接，**上游产物是下游唯一事实源**。没有"跳过解析直接写用例"，也没有"不评审直接跑脚本"。整条链路的纪律性，就是质量保障的来源。

## 四、质量保障机制
这套体系真正可靠的地方，不在于"能跑"，而在于**它拒绝哪些事**：

+ **拒绝跳过门禁**：解析对账、拆分校验、规范校验、渲染校验、覆盖率校验、评审校验、准入读取、环境门禁、独立回放——任一未过，流程不前进。
+ **拒绝编造内容**：用例与需求由模型逐条语义生成，脚本只做格式转换与校验，**不批量生成业务内容**。
+ **拒绝沿用旧结论**：需求、用例、脚本或数据变更后，旧指纹失效，**必须重新验证**，不能盖"已验证"章。
+ **拒绝掩盖缺陷**：产品 bug 固化为失败测试，**不改预期、不删断言、不用 xfail**。缺陷就是缺陷，复现就是复现。
+ **拒绝无环境执行**：没有用户明确提供的测试地址，不打开测试站点、不发业务请求。**杜绝AI自己猜环境跑出假绿**。

> 这些"拒绝"才是管理者真正应该关心的——它们决定了自动化结果能否被信任。
>

## 五、适用场景
| 场景 | 价值 |
| --- | --- |
| 新项目从 0 搭建测试体系 | 直接获得"需求→回放"全链路规范，不走弯路 |
| 已有大量手工用例的团队 | 把存量用例结构化、评审化、可自动化化 |
| 自动化率高但维护成本重的团队 | 用探索固化替代手写脚本，降低定位器维护负担 |
| 强审计、强合规行业（金融/政务） | 全程留痕、凭据可查、缺陷不掩盖 |
| 多环境、多版本并行交付 | 独立回放 + 环境门禁，换环境不换结论 |


## 六、落地路径
1. **导入需求**：把 Word / PDF / 图片 / Excel 放入 `input/`，触发解析 → 拆分 → 理解，产出带 REQ 编号的需求规范。
2. **设计与评审**：基于需求逐条设计用例，逐条评审，生成 11 列 Excel 与评审凭据。
3. **提供环境**：明确给出测试地址，配置 `tests/.env`，通过环境门禁。
4. **探索与固化**：逐条在真实系统中探索，留存证据，固化为 pytest 脚本。
5. **独立回放**：`finalize_exploration.py --run` 记录真实退出码与指纹，回填结果。
6. **持续回归**：需求或用例变更时，从来源改起，受影响条目重新走门禁。
